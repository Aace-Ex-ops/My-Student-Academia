1 Project Overview & Core Mission
Project Core Scope & Purpose

A full-stack, 3-tier web-based Course Registration & Academic Management System designed to replace error-prone manual enrollment workflows with automated prerequisite graph verification, hard semester credit ceiling enforcement, real-time section seat tracking, and automated FIFO waitlists.

Key Problems Solved
  • Eliminates Double Booking: Automated collision detection & seat locks.
  • Prevents Credit Overload: Hard system cap at 24.0 credits per semester.
  • Zero Prerequisite Violations: Real-time dependency graph checking.
  • Automated Fairness: Dynamic 1-up FIFO queue promotion on drops.

6 Core Business Rules (Validation Engine)
BR-01 & BR-02: Academic Constraints
  • BR-01 (Credit Ceiling): Maximum hard ceiling of 24.0 credits per student per term:
    CurrentCredits + CourseCredits ≤ 24.0
  • BR-02 (Prerequisite Compliance): Advanced courses require verified prior passing grades in all prerequisite courses.
BR-03, BR-04 & BR-05: Queue & Concurrency
  • BR-03 (Duplicate Guard): Blocks registering multiple sections of the same course in one semester.
  • BR-04 (FIFO Waitlist Promotion): Releasing an enrolled seat triggers atomic promotion of Rank 1 waitlist student and shifts remaining ranks ($N-1$).
  • BR-05 (Term Window Lock): Operations check Term.registrationOpen === true.
7 Non-Functional Requirements (NFRs) & Security Architecture
Performance & Concurrency
  • Catalog queries: ≤ 100 ms.
  • Enrollment mutations: ≤ 250 ms.
  • Supports 1,000+ concurrent users during peak registration windows without deadlocks.
  • In-memory cache with 60s TTL.
Security & Protection
  • Password Hashing: Bcrypt (salt rounds ≥ 10).
  • Tokens: JWT Bearer auth (8-hr expiration).
  • Injection Shield: Parameterized Prisma queries (Zero SQL Injection).
  • Encryption: HTTPS / TLS 1.2 & 1.3 over port 443.
Safety & Availability
  • ACID Transactions: Full rollback on any validation/capacity failure.
  • Availability SLA: ≥ 99.9% uptime.
  • Disaster Recovery: Write-Ahead Logging (WAL) & 24h snapshot backups.

9 Top High-Frequency Viva Questions & Model Answers
Q1: Why did you choose the Agile Incremental Iterative model over the traditional Waterfall model?
Answer: Waterfall requires static requirements upfront and delays testing until the very end, making prerequisite changes or UI refinements catastrophic. The Agile Incremental model allowed us to develop 4 distinct sprints (Auth, Engine, Portals, Cloud Integration), test ACID transactions early, and continuously refine validation business rules.
Q2: How does the system handle race conditions when two students click "Register" for the last available seat simultaneously?
Answer: We wrap the seat check, capacity decrement, and enrollment insert within an atomic ACID database transaction using Prisma's $transaction(). The first transaction acquires a lock, decrements the quota, and commits; the second transaction encounters a capacity of 0, rolls back cleanly, and offers the student a position on the FIFO waitlist.
Q3: How is the Prerequisite relationship designed in the relational database schema?
Answer: It is implemented as a self-referencing many-to-many relationship on the Course entity via a dedicated bridge table Prerequisite containing courseId and prereqCourseId, enforced by a composite unique constraint @@unique([courseId, prereqCourseId]).
Q4: How are Single-Page Application (SPA) 404 errors prevented when deploying to Cloudflare Pages or Firebase Hosting?
Answer: In SPAs, routing is handled client-side. To prevent 404s on browser reloads of routes like /catalog or /dashboard, we configured frontend/public/_redirects with /* /index.html 200 for Cloudflare Pages, and "rewrites": [{ "source": "**", "destination": "/index.html" }] in firebase.json.
Q5: What mechanisms ensure data security and prevent SQL Injection attacks?
Answer: Passwords are protected using salted Bcrypt hashing (work factor ≥ 10), authentication uses cryptographically signed JWT Bearer tokens, and SQL Injection is completely mitigated because Prisma ORM generates parameterized queries, preventing malicious SQL strings from executing.
Q6: What is the FIFO Waitlist promotion algorithm?
Answer: When an enrolled student drops a section, the backend executes a drop transaction, queries the Waitlist table for the entry with position = 1 for that section, verifies the candidate's credit limit (≤ 24 credits), converts their status to ENROLLED, and decrements the rank of all remaining waitlisted students by 1.
